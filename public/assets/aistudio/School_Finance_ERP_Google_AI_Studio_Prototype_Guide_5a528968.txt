Important source-to-prototype note
The database dictionary provides proposed backend keys such as company_id, ledger_id, voucher_id and bank_account_id. These are not all fields a human should type. In the prototype, display a friendly label such as "Company name"; keep system keys hidden and generate mock IDs automatically. Show the database key in this guide so the development team can connect each screen to the intended data model.
Do not use real data
Use fictional school names, fake bank account numbers, test payment references and sample employees. Do not paste real API secrets, bank credentials, PAN, Aadhaar, student personal data or production exports into an AI prompt.


1. How to use this guide in Google AI Studio
Google AI Studio Build mode can create web applications from natural-language prompts. Google documents the web app path as a client-side frontend (React by default) plus a server-side Node.js runtime. The live preview can be refined through follow-up prompts; projects can also be reviewed in code and exported or synced for further development. For this task, use it to create an interactive prototype with mock data, not a live financial system. [1]
1.1 Start the prototype
1. Open Google AI Studio and choose Build mode.
2. Select the Web app option (not Android) for the school finance admin portal and Parent Portal.
3. Paste the Global Prototype Prompt from Section 8.1.
4. Allow the first version to generate. Review the live preview and check the navigation before asking for detailed modules.
5. Paste one module prompt at a time from Section 8.2 onward. Ask the builder to extend the existing project rather than replace it.
6. After each module, click through every button and form. Ask AI Studio to fix broken navigation, validation and state updates.
7. When the prototype is stable, inspect the generated code and export/sync it for engineering review. Do not deploy it as a production finance application without the controls in Section 10.

1.3 Prototype expectation
Every screen should support the happy path with mock data: open a page, enter or select values, save, see a confirmation, and see the resulting record in a list or detail view. Use local component state or seeded mock data. A refresh may reset the demo unless the prototype deliberately uses safe local persistence.


2. Prototype boundaries and design rules
2.1 What the prototype must demonstrate
* A school organisation with one or more legal companies and branches.
* Accounting masters: account groups, ledgers, Cost Centres and voucher types.
* Student fees: fee plan ? invoice ? parent payment ? receipt ? accounting posting.
* Banking: bank account master ? linked bank ledger ? Bank Book ? bank statement import ? reconciliation.
* Procurement: request ? approval ? purchase order/bill ? payment ? reconciliation.
* Payroll: employee ? salary setup ? payroll preview ? approval ? salary payment.
* Parent Portal: parent login ? authorised child selection ? outstanding fees ? payment ? receipt history.
* Reports: operational summaries and financial reports with drill-down examples.
2.2 What must remain mock-only
AreaPrototype treatmentBank connectivityUse fictional bank account details. Do not connect to real bank APIs.Payment gatewaySimulate success, pending, failed and refunded states. Do not collect live money.AuthenticationUse demo role selector or mock sign-in. Do not use real passwords.Accounting postingShow sample balanced journal lines. Do not claim the prototype is an audited ledger.GST / TDS / PF / ESIUse sample values labelled illustrative. No live statutory calculation engine.Data storageUse local mock data. Do not upload real school data or personal records.NotificationsShow simulated in-app/email/SMS notifications, not real messages.
2.3 Visual design direction
* Professional school finance SaaS: clean, modern, trustworthy and not overly decorative.
* Use a left sidebar for modules, a top bar for company/branch/financial-year context, and a main content area.
* Use a neutral light background, navy text, restrained teal/blue accents, readable tables and clear status chips.
* Use consistent forms with labels above inputs, helpful field hints, required markers and inline validation.
* Use summary cards only for important totals: collections, outstanding fees, expenses, bank balance and pending approvals.
* Use responsive layouts: desktop-first for finance staff, mobile-friendly for Parent Portal.
* Use tables with search, filters, sorting, pagination and row-level actions such as View, Edit, Approve or Export.

3.1 Role behaviour to demonstrate
* Accountant creates a vendor payment; Finance Head approves it.
* Branch Cashier records a fee receipt only for their assigned branch.
* Student Fee Administrator prepares a fee plan; Finance Head or School Administrator approves publication.
* Payroll Officer prepares salary; authorised approver reviews it before payment.
* Auditor can view posted vouchers and audit logs but cannot edit them.
* Parent can view multiple linked children but cannot open another family's record.
Prototype simplification
Use role-based page visibility and disabled actions for demonstration. In production, enforce permissions on the backend for every API and record; hiding a button is not security.

10. What must change before production
A Google AI Studio prototype is useful for reviewing navigation, screens and user experience. It is not a production-ready accounting system merely because the app preview runs. Before using real financial data, engineering must replace mock state with a secured backend, tested database and approved accounting rules.
Prototype featureProduction requirementDemo role switcherReal authentication, server-side authorisation and session managementMock data/local stateRelational database, API validation, backups and audit controlsSimulated accounting postTransactional double-entry posting engine and immutable posted historyFake gateway checkoutProvider integration, signed webhook verification, idempotency and refund controlsSample bank CSVBank-specific file parsing, duplicate detection, secure storage and reconciliation testsDemo bank detailsEncryption, access masking, secret management and security reviewIllustrative tax calculationsCurrent effective-dated statutory rules approved by qualified advisersClient-side role hidingBackend permission checks and company/branch-level data isolationSample reportsReproducible reports sourced from posted ledger entries with drill-downPrototype approval buttonsMaker-checker workflow, approval limits and audit trail
10.1 Key technical controls
* Use UUIDs or a consistent ID strategy; do not let users type raw foreign keys.
* Enforce company and branch scope on every relevant API.
* Use decimal types for money; never use floating-point storage for accounting amounts.
* Use database transactions when posting voucher headers, lines and source status.
* Prevent duplicate provider payment events and duplicate statement imports.
* Keep bank account numbers and gateway credentials out of client-side code.
* Use reversal or adjustment entries for posted financial corrections.
* Run accounting, privacy, security and reconciliation tests before go-live.
